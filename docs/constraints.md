# Standing rules, gates and settled decisions

This is the single source of truth for what EDUNEXUS may not do, what it cannot do yet, and what has already been decided. Read it before [the roadmap](roadmap.md): where the two disagree, this file wins and the roadmap is wrong and should be corrected.

It exists because "not built yet" and "must never be built" are different statements that read alike in a requirements list. A rule below is permanent. A gate is a thing that is blocked, by a named decision, held by a named party. Anything in neither table is ordinary work.

## Standing rules

Never violate these. Changing one takes an explicit written instruction, recorded in the table.

| Rule | Why | Changed by |
|---|---|---|
| Teachers read only the learners in the classes they advise. Changing a learner record is a manager's — **with three exceptions**, each decided and each narrow: the adviser's historical encoding (2026-11-03), taking an already-registered learner into a class they advise, and registering a new learner into it (both 2026-11-05) | The manuscript's two statements conflicted and the user chose manager-only; the three exceptions were asked for afterwards and are recorded in the decisions table with their dates and their limits. **The read scope never widened** — row security is untouched — and no profile correction, LRN, grade change or withdrawal is open to a teacher | User instruction, then three revised workflows |
| **Nothing computes a grade** — no total, average, percentage, MPS, GWA or transmutation, anywhere, including client-side in the UI | Grades on the forms are the ones advisers enter from the DepEd ECR (2026-10-08). The arithmetic is DepEd's, not ours, and a wrong rule silently corrupts real report cards | Nothing. This is no longer merely gated: calculation was superseded by entry |
| Do not invent official grading rules, weights, transmutation, rounding, a passing mark or numeric Kindergarten grading | EDUNEXUS is not the authority on DepEd policy | The school supplying the rule, via the grading gate below |
| **Absence of a record is not evidence.** An unmarked attendance session and an unrecorded score are `null`, never zero and never "present" | Several modules exist specifically to preserve this; so does `Unrecorded` in the interface | Nothing |
| **Attendance figures come only from the school's recorded rule**, computed in `src/modules/forms/attendance.ts` and nowhere else. With no rule, an unmarked session, an unset date or an alternative-delivery date, the figure is **empty, never estimated** | An estimated attendance figure on an official return is a fabricated record | Nothing |
| **The SF10 is one cumulative record per learner, derived on every read, and it begins at Grade 1** | It is never a stored document, there is no per-year SF10, and Kindergarten is the credential presented for Grade 1 rather than a scholastic block (2026-11-03, 2026-11-04) | Nothing short of a DepEd form change |
| **Every SF4 figure is counted by section**, and a registered learner with no class is reported on their own, never folded into a rollup | A grade subtotal must equal the rows printed above it (0052, 2026-11-04) | Nothing |
| Never weaken database permissions, version checks or audit history to make a workflow easier | These are the correctness and privacy boundary, not an implementation detail | Nothing short of a redesign |
| Never modify an already-applied migration; add a new one | Applied migrations are checksummed and the runner refuses a modified file | Nothing |
| Never commit or expose credentials from `.env` or `.local` | Real school deployment secrets | Nothing |
| Use synthetic data in tests, and roll back hosted test fixtures | Real learner data is sensitive personal information under the Data Privacy Act | Nothing |
| The manuscript stays in its original location and is never committed | It is source material, not a repository artifact | Nothing |
| Do not weaken backend controls so a frontend workflow is easier to build | The API is the authority; the UI is a convenience over it | Nothing |
| **Never run `supabase config push`** | The pull deliberately skipped settings it could not represent, so a push would write local defaults over them, including disabling Twilio | Nothing |

## Gates

Each of these is blocked on information EDUNEXUS cannot derive. Do not build past one. Do not approximate it with a default.

| Gate | What it blocks | Who decides | Opened by |
|---|---|---|---|
| **Privacy owner and approved purposes** | Importing any real learner data. **This is the most important gate in the project**: until it opens, the hosted database holds synthetic records only | School | A named privacy owner, approved purposes and fields, hosting arrangements, recovery objectives and a *tested* restore |
| **Subject-teacher access** | Three teachers recording anything for the classes they actually teach but do not advise | School | **Raised 2026-11-04; integration deferred 2026-11-05 because the role itself is unconfirmed, so this gate now has a prior question: does the school run this role officially, and what is it called?** The school's own SF4 shows three teachers teaching across sections they hold no advisory for (Science and MAPEH in Grade 4; Araling Panlipunan with GMRC and with MAPEH across Grades 5 and 6). The formulas themselves arrived 2026-09-19 with the school's SF2; the rules for feeding them did not, and the form's single daily column raises the question of whether the school keeps two-session registers at all |
| **Official form templates** | The Kinder and Grades 1–3 SF9 cards, and the process for correcting an *already-issued* form | School | Blank approved templates, named signatories, and a release/correction process. **Partly open since 2026-09-19, and wider since**: the SF2, the SF4, the Grades 4–6 SF9 and the SF10-ES workbook are in hand with their signatories, cross-checked 2026-10-12, and printing is measured in real Chrome. **Outstanding:** the blank Kinder and Grades 1–3 SF9 — the two built layouts came from the school's spreadsheets rather than an official blank, and `sf9Get` refuses Kindergarten with `NO_KINDERGARTEN_CARD`; the correction process for an already-issued form; whether Balili's head should be pre-printed on the SF9's Cancellation block, which the *receiving* school completes; and which DepEd order the SF10-ES footer should cite — it prints *"Revised 2025 based on DepEd Order No. 10, s. 2024"* from the school's own workbook, while the 4 November clarification cites **DepEd Order No. 58, s. 2017**. | **Absence-alert rule** | Automatic alerts, thresholds, notifications, any messaging on attendance | School | A written approved rule. The school has confirmed it has none — but its own SF2 obliges the adviser to intervene at five consecutive absences and counts those learners monthly. **Contested since 2026-09-19**; the gate stays shut until the school says which is current. Follow-up stays manual and nothing alerts, messages or notifies |
| **Learner fields and class capacity** | Registry acceptance, additional profile fields, capacity enforcement, school-reviewed sample mappings | School | A reviewed field list and capacity policy, **or a written statement that there is no maximum**. Observed sizes are known since 2026-09-19 — 18–20 in Kinder, 29–37 elsewhere — and observation is not policy. Next year's classes enforces and suggests no maximum, deliberately. **Three fields have left this gate, each by the user's own explicit decision**: `learners.address`, one nullable line, for the initial learner-information import (0053, 2026-11-04); and `learners.guardian_name` and `learners.guardian_contact`, both nullable, asked for by name on 2026-11-05 **after** being shown in those words that this gate blocked them (0056). It stays shut for every other field — mother tongue, religion, indigenous group, a relationship-to-learner field, a second guardian, a guardian email, occupation or address, the **learner's own** contact number, or any breakdown of the address line into columns — and the reviewed field list is still what opens it. `tests/registry-guardian.test.ts` and `tests/registry-address.test.ts` assert every one of those is refused with a 422 rather than silently dropped. **What the school is still owed has not changed**, and now matters more rather than less: the guardian pair is personal data about an adult who is not the learner, held for 897 families |
| **Load and recovery verification** | Section 7 turnover | Operator, with targets agreed with the school | 27+ concurrent *hosted* session testing, backup restoration into an isolated project, privilege revocation and rollback drills. `npm run test:race` and `npm run test:load` pass locally; hosted throughput, realistic multi-session authentication load and every concurrent locking race are **not** established |
| **Real staff sign-in and school acceptance** | Hosted acceptance sign-off for Section 1, and the UAT and TAM evaluation | School and the deployment operator | A completed invited-user password setup and an authenticated API check. **Half open since 2026-09-21**: the user reported being signed in as the school principal and met a manager-only refusal, which only an authenticated manager can reach. School acceptance is still outstanding |
| **Service-role key in the runtime** | Any feature needing the key *in the API runtime*, such as deleting or altering an existing identity. **Since 2026-11-09 one request waits here:** naming whether the **email** or the **password** was the wrong one on a refused sign-in. Supabase answers both with the same `invalid_credentials`, so telling them apart means asking whether the address exists, which needs this key. It is also an account-enumeration leak in its own right (see the settled row of that date), so opening this gate is necessary but not sufficient | School and the deployment operator | An explicit written decision accepting that a compromised runtime could then create, alter or delete any Auth identity. Account creation no longer needs this: the key is confined to an isolated Edge Function that can only invite an address |

## Using this file

When planning an increment, check the gates first. If the work sits behind a closed gate, it is blocked: say which gate and stop, rather than approximating the missing decision. Every step in [the roadmap](roadmap.md) names the gate it depends on, or states **Gate: none**.

When the user's instructions and this file disagree, ask before building. That ambiguity is what this file exists to remove, and a wrong guess is expensive in a system that will hold real learner records.
